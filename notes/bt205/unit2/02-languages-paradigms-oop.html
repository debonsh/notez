Languages, Paradigms & POP vs OOP

Dec-2020 Q3b literal: "Differentiate Procedure-Oriented vs Object-Oriented languages". Plus OOP characteristics = recurring short question. Both live here.

Programming intro + program design steps

Programming = writing instructions a computer executes to solve a problem.
Design order: understand problem → plan (algorithm/flowchart) →
code → test/debug → document → maintain.

Categories of languages (3 levels)

LevelFormTranslatorExample
Low: machine0s and 1s onlyNone (direct)10110000 01100001

Higher level = more portable, less control; lower level = faster, machine-locked. C++ sits high but close to hardware — why RGPV teaches it.

OOP: an object binds data and methods

POP vs OOP — 6-row exam table (Dec-2020 Q3b)

#POP (C)OOP (C++)
1Program = list of functionsProgram = interacting objects
2Data and functions separate; global data sharedData + functions bound in class; private by default
3Top-down designBottom-up design
4No inheritance/reuse; copy-paste codeInheritance + polymorphism → reuse
5Less secure (any function edits data)Secure (encapsulation hides data)
6Example: C, Pascal, FORTRANExample: C++, Java, Python
OOP memory hook: encapsulation wraps, inheritance reuses, polymorphism gives one name many forms, and abstraction hides how. POP starts with functions and works top-down; OOP starts with objects and builds bottom-up.
Worked OOP model: a library can use Book(title, fine), Member(name), and Transaction(date) classes. Encapsulation keeps fine inside Book, inheritance reuses Member for student and faculty types, and polymorphism lets one fine-calculation call use the correct rule.

Solved C — one-line distinctions (2-mark shorts)

PairAnswer line
Compiler vs interpreterWhole program → object file vs line-by-line execution
Encapsulation vs abstractionWrapping data+fns vs hiding how, showing what
Overloading vs overridingSame name different params (compile time) vs child redefines parent (run time)
Concept traps
  • C is NOT OOP: C = procedural (no classes/objects). C++ adds OOP to C. Saying "C is OOP" = zero.
  • Top-down vs bottom-up: POP breaks big task down (top-down); OOP builds objects up (bottom-up). Reversed = lost mark.
  • Abstraction ≠ encapsulation: encapsulation wraps; abstraction hides. Pair them, never merge them.
  • Python IS OOP (everything is an object) — valid example alongside C++/Java.
Special lines for extra marks
  • "In POP data is a shared playground; in OOP each object is a fenced garden — encapsulation is the fence."
  • "Inheritance models real hierarchies once and reuses them forever: write Vehicle, derive Car, Bus, Truck."
  • "Polymorphism is one interface, many implementations — the same call behaves per object."
  • Close comparison answers with a scale line: OOP wins as software grows.

  • Language categories: 3 rows + translator column (assembler/compiler/interpreter).

Model answer · 7 marks

POP vs OOP

POP organizes a program around functions acting on separate data. OOP organizes it around objects that bind data and functions together.

POP (top-down): procedures act on separate data
+----------+       +---------------------+ acts on +---------------------+
| task     |------>| procedure f1()      |-------->| data A              |
+----------+       +---------------------+         +---------------------+
           |       +---------------------+ acts on +---------------------+
           +------>| procedure f2()      |-------->| data B              |
                   +---------------------+         +---------------------+
Functions and data remain separate; arrows mean calls/actions, not a pipeline.

OOP (bottom-up): data and methods are bound in an object
  +--------------------------------+       +------------+
  | Car object                     |------>| system     |
  | data: speed, fuel              |       |            |
  | methods: start, stop           |       |            |
  +--------------------------------+       +------------+
  1. Unit of design: functions/procedures versus interacting objects.
  2. Data handling: separate shared data versus data bound with methods and hidden by access rules.
  3. Direction: top-down decomposition versus bottom-up object construction.
  4. Reuse and safety: copy-paste/global access versus inheritance, polymorphism, and encapsulation.
  5. Examples: C/Pascal/Fortran versus C++/Java/Python.

Exam close: “As software grows, OOP reuses behaviour and protects data; POP is simpler for small programs.”

Model answer · 5 marks

Four OOP pillars with examples

Write E-I-P-A in order and attach one concrete example to each pillar.

OOP principles: E-I-P-A
+------------------------------------------------------+
| Object boundary: E-I-P-A                             |
| +----------------------+    +----------------------+ |
| | E Encapsulation      |    | I Inheritance        | |
| | private balance      |    | Vehicle is base for  | |
| | public deposit()     |    | Car, Bus, Truck      | |
| +----------------------+    +----------------------+ |
| +----------------------+    +----------------------+ |
| | P Polymorphism       |    | A Abstraction        | |
| | area(r), area(l,b)   |    | drive Car without    | |
| | one call name        |    | engine details       | |
| +----------------------+    +----------------------+ |
+------------------------------------------------------+
  1. Encapsulation wraps data and methods and hides implementation behind a public interface.
  2. Inheritance reuses a base class and extends it for a specialised type.
  3. Polymorphism lets one interface or name select the correct implementation.
  4. Abstraction exposes what an object does while hiding how it does it.

Exam close: “Encapsulation protects, inheritance reuses, polymorphism adapts, and abstraction simplifies.”

Model answer · 3 marks

Language categories + translators

Move from machine code to assembly to high-level language and name the translator at each level.

TRANSLATION (execution path)
High-level source ---> compiler / translator ---> machine code
+----------------------+    +------------------------+    +--------------+
| C, C++, Java         |--->| compiler / translator  |--->| machine code |
| if (x == 0) { ... }  |    |                        |    | 0 / 1        |
+----------------------+    +------------------------+    +--------------+

Assembly source ---> assembler ---> machine code
  +----------------------+    +------------+    +--------------+
  | assembly source      |--->| assembler  |--->| machine code |
  +----------------------+    +------------+    +--------------+

INCREASING ABSTRACTION (classification only; not a translation path)
LOWER ABSTRACTION    machine code    assembly    high-level source    HIGHER ABSTRACTION

Program design order: understand, plan, code, test, document, maintain
  1. Machine language uses binary digits and runs directly on hardware.
  2. Assembly uses mnemonics and needs an assembler.
  3. High-level languages are readable and need a compiler or interpreter for execution.

Exam close: box the three language levels and pair every level with its translator.
